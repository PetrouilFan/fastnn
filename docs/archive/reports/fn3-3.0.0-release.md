# FastNN 3.0.0 release report

The 3.0.0 stable candidate is the tip of `rewrite/fastnn-3` that carries this
report. It descends from the alpha review commit `672cec9` and the audited wave
report `7836a65`. `main` is untouched at `a2c0759`; no tag, GitHub release,
package publication or pull request has been created.

This report is the release record: what is claimed, the evidence behind each
claim, what is deliberately not claimed, and what the owner still has to
decide. It is written to be read with the raw logs it cites.

---

## 1. Declared release scope

| Dimension | Claimed |
|---|---|
| Platform | Linux x86_64 |
| Rust crate | `fastnn` 3.0.0, default features, plus `vulkan`, `cli`, `fn3` and fault-injection targets |
| Python wheel | `fastnn` 3.0.0, CPython 3.11+ abi3, manylinux x86_64, **CPU inference only** (see below) |
| Models | pinned tiny GPT-2 (27,897,974 B) and pinned trained GPT-2 (498,126,358 B, 12 layers, hidden 768, vocab 50,257) |
| Precision | FP32, and opt-in INT8-weight / FP32-activation (`fn3-quant-format-v1`) |
| Backends | CPU reference implementation; Vulkan 1.1 on the NVIDIA GTX 1080 Ti through the crate and the `fastnn-infer` CLI |
| Execution | artifact-only (`prepare` once, then run with no ONNX source), prefill and cached decode |
| Input | token IDs only; no tokenizer |

The wheel is built from `[tool.maturin]` with the default feature set, which
does not include `vulkan`; a clean install lists `devices ['cpu']` and cannot
serve a Vulkan request. The `vulkan` feature is claimed for the crate and the
CLI, where it is gated and measured. Shipping Vulkan inside the wheel is a
deliberate non-claim of this candidate: it would expose a device through
`fastnn.inference` that no Python test exercises on the GPU, so it is recorded
in §13 instead of being slipped in at release time.

Not in scope and not claimed: CUDA (#77), training (#78), other GPU vendors or
drivers, macOS/Windows inference, arm64, batching above 1, sequences above the
1024-position envelope, and quantized speedups.

## 2. Support matrix

"Built" means a build artifact was produced from the candidate. "Installed"
means it was installed outside the checkout. "Inference" means a full
prefill + cached decode produced the pinned top-k. "Physical" means the Vulkan
row ran on the named device with validation enabled and zero messages.

| Combination | Built | Installed | Inference | Physical |
|---|---|---|---|---|
| Linux x86_64, CPU, FP32 | yes | wheel | yes (tiny, trained) | n/a |
| Linux x86_64, CPU, INT8 | yes | wheel | yes (tiny via wheel, trained via CLI) | n/a |
| Linux x86_64, Vulkan, FP32 | crate + CLI, source build | crate from source; no CLI binary attached | yes (tiny, trained) | yes |
| Linux x86_64, Vulkan, INT8 | crate + CLI, source build | crate from source; no CLI binary attached | yes (tiny, trained) | yes |
| Linux x86_64, Vulkan, staged diagnostic | crate + CLI, source build | crate from source; no CLI binary attached | yes (tiny) | yes |
| macOS / Windows | wheel | hosted CI import only | **no** | n/a |
| arm64 | **no** | no | no | n/a |

"Installed" is true for Linux x86_64 only; the macOS and Windows wheels are
built and import-smoked by the hosted matrix, nothing more. The wheel does not
carry the `vulkan` feature, so the Vulkan rows are not wheel capabilities.
`fastnn-infer` is a **source build**: the release workflow builds and attaches
wheels only, so no CLI binary is installed or shipped by it, and the CLI is
produced with
`cargo build --release --no-default-features --features cli,vulkan --bin fastnn-infer`.
The `cli` feature is a target gate, not a dependency set. The physical INT8
row is the automated trained gate plus the tiny CLI run, not a hand-typed
sample: `fn3_trained_int8` asserts 48/73 coverage, the padded payload, zero
staged prepare traffic, zero input readbacks, exact top-1, the KL and centered
bounds from the format decision, and validation 0/0, and it fails rather than
skips when its model or device is absent.

The single physical device is `NVIDIA GeForce GTX 1080 Ti`, UUID
`471b2bda-51e1-6451-e692-ff5d1e146f1e`, driver 580.196.07, 11,264 MiB.
`lavapipe` enumerates as a separate software adapter and is never allowed to
satisfy a physical row: the test harness rejects `software=true` and
`FN3_VK_REQUIRE_PHYSICAL=1` fails when the UUID does not match.

## 3. Trained resident Vulkan (#70)

The alpha blocker was `Reshape(input_ids) → Gather(wte)`: the resident session
placed the identity reshape's output on the device, and `Gather` validates
indices on the host, so the trained prefill failed with `NotImplemented`. Two
fixes landed:

- `14adee3` folds a provably identity `Reshape` into its input slot at plan
  time, so `Gather` reads the host `input_ids` graph input.
- `95a44e9` narrows the fold to what the session can prove: declared output
  shape validated, equal shape/dtype/element count and layout semantics,
  graph outputs excluded, and only a session-owned contiguous host i64
  `input_ids` aliased. Public plans keep the copy, strided CPU bindings still
  work through both execute paths, and the `Gather` bounds check is unchanged:
  an oversized or negative index still produces a typed out-of-bounds error.
- The resident step batch reservation was raised from 512 to 1024 descriptor
  sets because the trained plan is 774 op records. A larger plan still fails
  explicitly; splitting a step is not implemented.

Verified on the candidate, artifact-only, physical GPU, validation enabled:

| Check | Result |
|---|---|
| Plans at `seq=13,past=0` and `seq=1,past=13` | 774 instructions; `Gather` index slot is `input_ids` `GraphInput`; identity node `FoldKind::Identity` |
| Resident device executions proven | 2,321 / 2,321 |
| Input readbacks | 0 |
| Resident weight upload | 18,156 B (staged control 530,260,200 B) |
| Resident vs staged logits | `max_abs 0.0`, `mean_abs 0.0`, same top-1 every phase, top-5 5/5 |
| Prefill vs pinned ORT | `max_abs 1.869e-4`, `mean_abs 1.006e-4`, 0 elementwise violations, top-1 640, top-5 5/5 |
| Decode 1 / decode 2 | top-1 11 / 262, top-5 5/5 |
| Validation | 0 errors, 0 warnings |

Staged mode remains available as `FN3_VK_STAGED=1` and is used only as a
diagnostic control; the resident path is the default. Long-context and peak
memory numbers are in `docs/reports/fn3-74-support-matrix.md`.

## 4. Quantized artifact inference (#70)

`fn3-quant-format-v1` is weight-only INT8 with FP32 activations: signed codes,
one binary16 scale and one int16 zero per 64-element group along K, one FP32
accumulator per group, no dequantized weight and no Q/DQ pair.

The opt-in is `--weight-int8` on `run`/`generate`, or `weight_int8=True` in
`fastnn.inference.load`. Packing happens from the loaded artifact at session
setup: the `.fnn3` format is unchanged and the default path is byte-identical.

Coverage on the pinned trained GPT-2 is 48 of 73 MatMuls per phase
(`attn.c_attn`, `attn.c_proj`, `mlp.c_fc`, `mlp.c_proj` in all 12 layers). The
25 fallbacks are the 24 attention products, whose right-hand side is computed
per step, and the tied LM head, whose right-hand side is `Transpose(wte)`.
Each instruction is wholly packed or wholly FP32; the report counts both.

| Evidence (artifact-only, physical Vulkan, validation on) | Tiny | Trained |
|---|---:|---:|
| Packed / total MatMuls | 8 / 13 | 48 / 73 |
| Max FP32-vs-INT8 logit delta | 0.00870 | 0.81710 |
| Max CPU-vs-Vulkan INT8 delta | 1.0e-4 | 6.1e-5 |
| Top-1, all measured steps | exact | exact |
| Top-5 | 5/5 | 5/5 prefill, 4/5 decode 1 and 2 (ORT gap 7.9e-4 / 1.0e-2 against centered error 0.158 / 0.145) |
| KL vs FP32 | — | 4.766e-6 / 1.455e-4 / 3.264e-4 (bounds 1e-3 / 2e-2) |
| Centered max / RMSE | — | 0.210 / 0.049 (bounds 0.8 / 0.25) |
| Packed payload | 417,792 B | 90,243,072 B |
| Packed source | 1,572,864 B | 339,738,624 B |
| Dense weights still FP32 | 26,260,132 B | 158,022,256 B |
| Avoided dense weight bytes | 1,155,256 B (4.2%) | 249,495,552 B (50.1% of the model) |
| Packed prepare traffic | 417,792 B | 90,243,072 B |

Those bytes are API counters (`Storage::len`, packed payload length), not RSS or
VRAM. The FP32 source weights stay resident in host memory, and the device
still holds one dense table for consumers that are not packed-only, so the
reduction is a weight-transport and storage fact, not a process-memory claim.

Latency is not a win and is not presented as one. On the trained model, packing
costs about 0.85–1.1 s per session, decode is 7–10% slower, and 1024-token
prefill is 2.36× slower on Vulkan (2.568 s vs 1.089 s FP32). Decode is at parity
at both measured contexts: 241.9 ms vs 243.6 ms p50 at 256 tokens, and 576.2 ms
vs 574.5 ms p50 at 1023 tokens (a 1023-token prefill followed by one decode).
The reason is that the packed
kernel is a scalar group loop, while the FP32 path uses the tiled kernel; the
benefit is that a session moves 90 MB of weights instead of 340 MB.

An FP32 and an INT8 session in one process peak at 3.40 GiB at 256 tokens and
both fail at 1023 tokens with `ERROR_OUT_OF_DEVICE_MEMORY` (6.63 GiB live,
6.91 GiB reserved, 6.72 GiB free). That is recorded as a limit, not a defect:
the duplicate weight copy is only +90 MB, and the window itself does not fit
twice on an 11 GiB card shared with the desktop.

## 5. Trained FP32 tolerance (#76)

Trained GPT-2 FP32 logits are compared against digest-pinned ONNX Runtime
references at prefill and two decode steps. Two aggregate bounds are enforced
on CPU and on default resident Vulkan:

```text
mean(|delta|) <= 5e-5 + 5e-6 * mean(|ref|)
rms(delta - mean(delta)) <= 5e-5 * rms(ref - mean(ref))
```

The elementwise bound, top-1/top-5 with margin, KL, finite-value and KV-cache
checks are unchanged. The previous fixed `5e-5` mean-absolute bound is still
evaluated and reported as a diagnostic; it fails five of six CPU/resident
phases, and that failure is visible in the log rather than removed.

The decision is evidence-driven: an independent float64 evaluation of the same
graph differs from ONNX Runtime by 6.254e-5 mean absolute at the same position,
so a fixed 5e-5 bound is below the reference implementation's own rounding
error. The observed error is a near-constant translation of the 50,257-vector
(residual centered RMS 2.2e-5–4.6e-5) that softmax removes; top-1 is exact and
top-5 overlaps 5/5 in every phase.

Negative controls prove both bounds can fail independently: an injected
constant offset trips only the mean bound, and an injected centered distortion
trips only the centered-RMS bound, while the elementwise and ranking checks
stay satisfied. Both run through the same enforcement path as the real gate. A
missing model, a missing reference payload, a malformed opt-in value and an
unmatched device UUID all fail with named errors instead of skipping.

Tiny-model tolerances are untouched.

## 6. Release-surface audit (#75)

Every candidate for removal was traced to its callers before deletion. The
result is a disposition table in `docs/internals/legacy-2x.md`:

| Surface | Disposition |
|---|---|
| `fastnn-runtime` binary, direct `clap` dependency | **removed** — no test, CI lane, example, script or packaging entry invoked it; 3.0 rejects its `.fnnc` plans by design |
| `fastnn-infer` CLI | kept and renamed to the canonical name; the `cli` feature is now only a target gate for `required-features` |
| `fastnn-convert` and `fastnn.io` (`.fnn`, ONNX/graph conversion) | kept; still the documented 2.x path, exercised end to end |
| AOT compiler, prepared executor, quantized CPU pipeline | kept; `quantized_pipeline`, `cpu_arena_telemetry` and `onnx_export_quantized` are the reference tests |
| Eager `Tensor` / `nn` API | kept; `import fastnn.inference` imports it, and it is the 2.x user surface |
| Legacy `backend::runtime::Runtime` and bincode plan I/O | kept, explicitly "not a 3.0 promise"; its decoder is covered by unit tests and the fuzz target |
| CPU baseline/oracle tooling and `fn3-bench` | kept as benchmark evidence |

Canonical names are now `fastnn::inference`, `fastnn.inference` and
`fastnn-infer`. The alpha names `fastnn::fn3`, `fastnn.fn3` and `fn3-infer` are
removed, not aliased; the internal directory is still `src/fn3` and the
`.fnn3` on-disk format, its magic and the plan fingerprint domain
(`fastnn.fn3.plan.v1`) are unchanged, so existing artifacts keep their
digests. Migration notes are in `docs/guides/migrate-from-2x.md`, including a
row that distinguishes the 3.0 runtime INT8 path from the 2.x AOT W4A8
pipeline.

Documentation truthfulness: a broken `fastnn.io` example was fixed (and the
two defects it exposed are recorded: `PyTensor` has no `copy_`, and
`io.save(format="fnn-v3")` writes the version prefix twice), the audit table's
coverage claims name the real tests, and the three log links that were never
committed were removed from the trained FP32 report rather than left dangling.

## 7. Release-path debt

Fixed in this wave, each with a regression:

| Defect | Fix |
|---|---|
| OOM reported `Allocation { bytes: 0 }` | reports the failed request size, or `AllocationSizeUnknown`; contract test pins both diagnostics |
| Loader panics and false acceptance | five defects fixed; every malformed case maps to a typed error; budgets bound allocation before it happens |
| KV half-append on a mid-commit device copy | recoverable failures roll back every layer to the pre-step extent; retry cannot double-append |
| Device loss left a session in a half-usable state | terminal failures poison the device and name the adapter, UUID and call; `recover()` is the only retry boundary |
| Identity `Reshape` on a host-validated index chain | folded at plan time (§3) |
| A stale wheel in the packaging `dist/` could be installed | unlinked before the build; the lane now fails rather than reporting the wrong artifact |
| A failed or timed-out fence wait could free, destroy or recycle resources the GPU may still reference | fixed in `f5fbdb4`: every in-flight buffer and allocator range, staging block, command/descriptor pool, descriptor set and fence moves to an owned device quarantine; a device-wide reference count frees a buffer only when its last submission reference is proven, so a buffer shared by two submitters survives one proof. It leaves only after a direct proof wait on that fence or after a successful teardown `vkDeviceWaitIdle`; a failed quiesce deliberately leaks (including the loader instance) rather than frees. `tests/fn3_vulkan_quarantine.rs` pins pre- and post-wait faults, implicit-drop, submit, end-recording, the shared-buffer case, release-once and both teardown outcomes |
| `Submission::Drop` retried a wait on a poisoned device | a failed implicit wait moves the submitter and its buffers to the quarantine; the token never retries and the pool never recycles it |
| The Python INT8 report used its own labels and survived `reset` | keys match the CLI labels exactly, `None` before the first step and after `reset`, and the tests parse a captured CLI line instead of restating the labels |
| The packaging lane proved only the FP32 wheel path | both FP32 and `--weight-int8` replays run as separate source-free processes, and the INT8 child asserts its own report |
| The ownership guides described the alpha host-storage limitation | corrected to the resident default and the real limits; both guides are inside the freshness bound again |

Two release blockers found after the candidate was cut are fixed and merged.
The fence-completion hazard is closed by the device quarantine (`f5fbdb4`)
described in the table above. The second is `PersistentKey` (`8f9d283`): the
table keyed by host storage address, which a freed model could hand to the next
model of the same geometry.
`Storage::generation` is now a process-global monotonic value (never an address,
never reused), and every table entry registers a drop hook on its host
allocation, so the device copy is released with the last `Storage` handle. The
regression is `tests/fn3_vulkan_persistent_identity.rs`: a dropped model A
followed by model B with identical geometry and different bytes, a second
session over one artifact with a 0-byte prepare, and create/drop cycles that
leave the table empty with the release counter accounting for every entry.

Deferred with reasons, recorded rather than hidden:

- **Concurrent `prepare` racing a staged-input check** in the same backend can
  reject an operand as a late upload after another thread publishes residency.
  Single-session use, which is what this release claims, cannot reach it.
- **`end_step` returns `Ok(0)` for a discarded partial batch.** The count is
  right; the success code does not distinguish it from an empty batch.
- **`MemoryStats::peak_live_device_local_bytes`** is not wired into the bench
  adapter, so a matched baseline reports the allocator high-water only.

Long-context decisions from the #74 measurements: staging pooling was **not**
pursued because the resident path moves 5.3 KB per chain and the staged path is
a diagnostic only; the extra KV queue submissions were **kept** and measured
(50 per decode, 48 of them KV copies) rather than optimised; transposes dominate
decode GPU time (`reduce_mean` 42.7 ms and `transpose` 25.3 ms of ≈70.8 ms at
1023 tokens) but are context-invariant, so they are recorded, not reworked;
duplicate FP32/INT8 storage is only +90.2 MB, so a shared packed table was not
prioritised.

## 8. Performance

All numbers are p50 unless stated, measured on the declared host under
`/tmp/opencode/fn3-measure.lock` with `/proc/loadavg` recorded. The host was
loaded during the sweep (loadavg 4.3–7.6) and the desktop held 4.17 GiB of
VRAM, so absolute latencies are upper bounds; the ratio comparisons are the
durable result. Device timestamps are not comparable run to run because the GPU
clock is not pinned (139 MHz idle / 1,911 MHz max); host wall clock is the
metric used everywhere.

| Result | Before | After |
|---|---:|---:|
| Vulkan prefill, tiny 10 tokens | 142.36 ms | 9.14 ms |
| Vulkan decode, tiny per token | 130.44 ms | 9.31 ms |
| Vulkan weight upload per chain | 318.9 MB | 5.3 KB |
| CPU tiny prefill, 1 thread | 270.8 ms | 13.96 ms (19.4×) |
| CPU tiny decode, 1 thread | 188.7 ms | 6.15 ms (30.7×) |
| CPU trained prefill, 1 → 16 threads | — | 1.38× |
| CPU trained decode, 1 → 16 threads | — | 1.04× |
| Auto thread budget vs best fixed | — | 1.01–1.034× |
| Quantized execution vs FP32 (CPU) | — | 26.56% of projection storage; prefill 1.48×, decode 1.10× faster |

Long context, resident Vulkan FP32: prefill 1,088.8 ms at 1024 tokens; decode
p50 154.9 ms at a 64-token context, 243.6 ms at 256 and 574.5 ms at 1023, where
the last figure is a 1023-token prefill followed by one decode; device
reservation grows to 6.38 GiB.
CPU FP32: 23.06 s prefill at 1024 and 946.6 ms for 1023+1, peak RSS 6.83 GiB.
Staged control at 256: 8.99 s TTFT and 1.98 s/token, 26.8× and 8.1× slower than
resident, with 1.31 GB uploaded for the prefill.

**Deferred by measurement, not by omission.** The #74 sweep and a read-only
decode profile identified four costs above the supported scope's needs, and the
candidate ships with limits recorded rather than late code changes:

| Cost | Measured | Why it does not block 3.0.0 |
|---|---|---|
| 50 `vkQueueSubmit` per decode (24 KV refreshes + 24 appends + 1 batch + 1 readback) | ~5–15 ms of the step | the step still meets the 574.5 ms envelope at 1023 tokens; moving the copies inside the batch needs new barrier proofs |
| 154 MB `Transpose(wte)` per token | 25.3 ms of the 70.8 ms decode GPU time | either +147 MiB resident or a transposed-RHS MatMul flag; a pre-stable memory trade, not a correctness one |
| staging pool held to the fence | device peak 62 → 116 MB on the resident path | the peak fits every measured context, including 6.26 GiB live at 1024 tokens |
| INT8 and FP32 weights coexist | +90.2 MB packed per session; two live sessions OOM at 1023 | the supported scope is one session; the duo limit is recorded in §4 |

The triage order for post-3.0 work is the profile's: coalesce KV copy rows
(294,912 → 288 regions per step), then the tied-head transpose, then the
decomposed `ReduceMean`, then slot-pool eviction. None of them changes a
result, and each needs a fresh parity sweep, which is why none is in this
candidate.

## 13. Release status and remaining decisions

3.0.0 was released on 2026-11-20 from this candidate:

- `main` fast-forwarded from `a2c0759` to `4db656e` (no merge commit, so the
  released commit is exactly the one hosted CI built).
- Annotated tag **`v3.0.0`** at `4db656e`; release workflow run **`44692913491`**
  green on every job — `validate-tag`, `quality`, three `portable-build` jobs,
  three `build-wheels` jobs and `create-release`.
- GitHub release <https://github.com/PetrouilFan/fastnn/releases/tag/v3.0.0>
  with `fastnn-3.0.0-cp311-abi3-manylinux2014_x86_64.manylinux_2_17_x86_64.whl`,
  `…-macosx_11_0_arm64.whl` and `…-win_amd64.whl`.
- CI on `main` at the same commit, run **`44692892883`**, green.

Decisions closed and still open:

1. **License.** MIT, confirmed by the owner before publication. The crate and
   every wheel declare it, read from the committed `LICENSE`.
2. **Platform claim.** Linux x86_64 inference is claimed; macOS and Windows are
   wheel install and import only; no arm64 inference claim despite the arm64
   wheel. Vulkan is claimed through the crate and the `fastnn-infer` source
   build, not the wheel.
3. **Vulkan in the wheel — still open.** One-line `[tool.maturin]` change, but it
   exposes a Python device no release has exercised on the GPU; it belongs to a
   follow-up that adds a GPU arm to `tools/ci/packaging_lane.py`.
4. **Recorded exceptions, not fixed here.** The concurrent `prepare` race and
   `end_step` returning `Ok(0)` for a discarded batch, plus the performance and
   memory trades in §8. The fence-completion hazard and the `PersistentKey`
   address alias are fixed (`f5fbdb4`, `8f9d283`), not exceptions.
5. **Package publication.** The GitHub release carries wheels; nothing was
   pushed to PyPI or crates.io.
6. **Operational note.** `validate-tag` in `release.yml` requires the tag to
   equal `origin/main`'s tip. This status note is one documentation commit past
   the tag, so re-running `Release` for `v3.0.0` will fail that check by design;
   the release itself is complete and does not need a re-run. Cut any future tag
   at `main`'s tip.

## 14. Reproduction

# Release build of the CLI from the candidate

fastnn-infer run --model model.fnn3 --tokens 464,2068,7586,21831,18045,625,262,16931,3290,13 \
  --decode 640,11,612 --device vulkan --weight-int8

  cargo test --release --features vulkan --test fn3_trained_parity -- --include-ignored

# Trained INT8 gate: coverage, KL, centered bounds, validation 0/0
FN3_TRAINED_INT8=1 FN3_TRAINED_ONNX=<pinned trained onnx> \
FN3_VK_REQUIRE_PHYSICAL=1 FN3_VK_VALIDATION=1 \
FN3_VK_DEVICE_UUID=471b2bda-51e1-6451-e692-ff5d1e146f1e \
