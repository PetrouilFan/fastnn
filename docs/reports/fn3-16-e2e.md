The CPU half was already proven by FN3-12. This issue had to delete the two

1. **No Vulkan plan could be built for the pinned graph.** `Planner` demanded

## 1. Fix 1 — concrete-operand preflight (`Backend::admits`)

### 1.1 The contract

`src/fn3/backend/mod.rs` gains one additive, defaulted trait method:

```rust
fn admits(
    &self,
    op: OpId,
    shapes: &[Shape],
    dtypes: &[DType],
    params: &OpParams,
) -> Support {
    let _ = (shapes, dtypes, params);
    self.supports(op)
}
```

`shapes` and `dtypes` are the instruction's operands in plan order (inputs,
then outputs) and have the same length; `params` are its encoded attributes.
Element types are part of the question because `Shape` carries extents only,
and the pinned graph's first refusal was exactly a dtype one: an op-level
`Partial` says "4- and 8-byte elements", which cannot be answered without the
operand dtypes. The task's suggested signature was
`admits(op, shapes, params)`; `dtypes` is the one addition, and it is what makes
the preflight dtype-aware as required rather than a broader claim in a table.

The default returns `supports`, so **CPU behaviour is unchanged** (the gate's
CPU numbers reproduce FN3-12 to the last digit):
`CpuBackend` implements no override, every previous verdict is reused, and the
contract tests (`fn3_contracts`, 43) and planner tests (11, including
`plan_rejects_an_op_without_full_support`) pass unchanged.

### 1.2 Why this does not make the backend lie

The Vulkan override is `KernelSet::admits` (`src/fn3/backend/vulkan/kernels/mod.rs`).
The honesty is structural, not editorial:

- `OpKernel` gains `admits: Option<AdmitFn>` with
  `AdmitFn = fn(&[Shape], &[DType], &OpParams) -> Result<(), String>`.
- `KernelSet::admits` switches on the **registered** verdict:
  - `Full` → `Full`, no rule consulted;
  - `Unsupported` → the same `Unsupported`, no rule consulted;
  - `Partial { reason }` → the rule is asked. `Ok(())` becomes `Full`; `Err(detail)`
    stays `Partial` and the message keeps the registration's reason plus the
    concrete conflict.
- A rule returns `Result<(), String>`, not a `Support`. It cannot invent
  `Unsupported`, cannot hide an op, and cannot claim `Full` by itself: `Full`
  only exists when the kernel is already registered *and* its own rule confirms
  the operands are inside the subset its reason names.
- The op-level table is untouched (`supports(Transpose)` is still `Partial`;
  asserted by the new unit test). The `vulkan_smoke` test still pins
  `Capabilities::dtypes == [f32]`.
- The launch function remains the execution authority: it re-validates every
  operand and returns the typed `UnsupportedOp` for anything outside the
  subset. The worst consequence of an over-permissive rule is a failed step
  with a clear error, never a wrong number and never a CPU fallback.

Two unit tests pin the mechanism: `a_partial_verdict_is_refined_by_its_concrete_rule_only`
(inside/outside for `Transpose` f32/i64/Bool, `Softmax` trailing/other axis,
`Where` f32/Bool values) and `a_rule_can_only_narrow_a_registration` (a rule
attached to a `Full` or `Unsupported` registration is ignored).

### 1.3 The rules, and what they can see

| Op | Registered subset | Admission rule |
|---|---|---|
| `Transpose` `Reshape` `Flatten` `Squeeze` `Unsqueeze` `Expand` | 4/8-byte elements | every operand width ∈ {4, 8} |
| `Slice` | one sliced axis, 4/8-byte elements | every operand width ∈ {4, 8} |
| `Split` | one axis, ≤ 16 outputs, 4/8-byte | every operand width ∈ {4, 8} |
| `Concat` | one axis, ≤ 16 inputs, 4/8-byte | widths ∈ {4, 8} and inputs ≤ 16 |
| `Softmax` | f32, trailing axis | f32, rank ≥ 1, resolved axis == rank−1 |
| `ArgMax` | f32/i32 in, i64 out, one axis | those dtypes, ≤ 1 axis |
| `Where` | f32/i32/i64 values, Bool condition | Bool condition, equal 4/8-byte values |

The rule sees shapes, dtypes and attributes. Some subset boundaries are
**value-dependent** and remain execution-time checks by the kernel: `Slice`'s
number of sliced axes (read from its i64 inputs), `Split`'s output count (a
`Split` plan carries one or two inputs, so the count is not recoverable from the
operand list alone), and any check that depends on integer *values*. That is a
deliberate, documented limit: an admitted instruction still cannot execute
outside its subset silently — the kernel refuses it with its own typed error.
Every instruction of the pinned graph is inside these subsets, which the runs in
§4–§5 demonstrate empirically.

### 1.4 Where the plan asks

`src/fn3/model/specialize.rs` replaces the bare
`supports(op).require_full(...)` with:

```rust
backend.admits(op, &shapes, &dtypes, &instruction.params)
    .require_full(op, backend.name())
```

`Survey::check_capabilities` keeps the genuinely backend-wide gates
(`max_shape_rank`, `max_buffer_bytes`) and no longer consults the aggregate
dtype table for a slot that an instruction touches. Every plan slot is an
operand of at least one instruction (dead values are pruned before slots are
assigned), so the per-instruction loop is a complete dtype gate; a slot no
instruction touches — a graph output that is a folded constant — falls back to
the aggregate table exactly as before. A `Partial` verdict still becomes
`UnsupportedOp` with "only partially supported: … (at plan instruction N, op X)",
so a concrete operand outside the subset is refused **before execution**.

## 2. Fix 2 — zero-length Vulkan buffers

Vulkan forbids `vkCreateBuffer` with `size = 0`, and `past = 0` needs a
zero-element concatenation input. The fix is in the buffer layer; `Concat` additionally
avoids allocating an input that contributes no byte:

- `context.rs`: `Buffer::new` computes
  `allocation_bytes = desc.size.max(EMPTY_BUFFER_BYTES)` with
  `EMPTY_BUFFER_BYTES = 4` and passes that to `vkCreateBuffer`, the limit checks
  and the suballocator. `Buffer::size()` keeps the **logical** size, which is
  `0`; `check_range` uses it, so no non-empty access is representable. The
  dummy word is a real bound allocation (the GTX 1080 Ti's allocator rounds it
  to a 16-byte suballocation), so ownership and teardown stay uniform.
  `write_from`/`read_into` are explicit no-ops for an empty slice rather than
  asking a device-local buffer for a host mapping.
- `kernels/pointwise.rs` (`Job`): zero-length uploads and readbacks get no
  staging lease, no copy, no barrier and no host readback. Only byte-producing
  buffers enter the transfer path.
- `kernels/transform.rs` (`Concat`): a zero-element input is not allocated or
  uploaded at all; it contributes no bytes and is not bound. This is the actual
  `past = 0` case. The destination extent and every other piece are unchanged.
- The recorder already rejects a zero descriptor range before recording
  (`submission.rs`), so a kernel that ever binds an empty buffer is a message,
  not undefined behaviour.
- `memory.rs` and `device.rs` needed **no change**: the suballocator already
  handles the 4-byte buffer's `VkMemoryRequirements` (16 B by alignment), and
  `flush`/`invalidate` already return early at length 0.

Direct evidence, on the physical GPU (`a_zero_element_buffer_is_real_but_unaddressable`):
logical size 0, 16 B reserved, empty upload/download are no-ops, a 4-byte upload
is refused as `CapacityExceeded`, `live_bytes` returns 0 → 0, no handle leaks,
validation delta 0/0. The same empty-input path is exercised by every device
prefill below; the allocation itself is exercised by this test.

allocates nothing and dispatches nothing; it is a structural no-op, not an
execution. The gate reports the plan census and requires
`records == byte-producing instructions` plus per-op equality. A decode step has
no zero-element instruction and is exactly **144/144** (576/576 over four
steps), matching FN3-12. The alternative — recording a fake dispatch over a
zero-length buffer so the literal count is 720 — would manufacture evidence that
the device did work it did not do, and was rejected.

### 5.6 Host-side shape work

The issue asks for it to be identified. The pinned plan has 144 instructions;
the surviving structural ops are `reshape` 24, `transpose` 11, `concat` 5,
`constant_of_shape` 2, `expand` 2, `slice` 2, `split` 2, `unsqueeze` 2 and
`where` 3 (plus `cast` 3). Every one of their **output elements** is produced by
a dispatch; what happens on the host is the small-integer metadata:

- **Plan time (FN3-10):** every extent is resolved and all integer shape
  arithmetic (`seq + past`, `total − seq`, the causal index range) is folded into
  constants. There is no surviving `Shape`, `Range`, `Equal`, `Less` or integer
  `Add`/`Sub`/`Mul`/`Div`/`Pow` instruction in the executed plan.
- **Execution time:** `Reshape`'s target, `Slice`'s starts/ends/axes/steps,
  `Split`'s sizes, `Expand`'s target and `Where`'s broadcast geometry are read
  from the plan's own (constant) operand tensors and validated on the host; the
  kernels then move or select bytes on the device. This is metadata validation,
  not a host computation of any output element, and it is what makes "reject,
  never approximate" affordable.
- **Session time:** the `position_ids` and `attention_mask` vectors are built on
  the host (a few `total` i64 values), and the live KV prefix is copied into a
  contiguous `[1, 2, live, 64]` buffer per layer per step (8.7 KB per buffer at
  17 tokens) because the Vulkan kernels reject strided operands. Logits are
  copied out at `[1, 1, 50257]` (201 KB). These are FN3-12's documented
  host-staged data paths, not shape work.

### 5.8 What "host staged" means here

Alpha `Tensor` storage is host memory on **every** device (`AlignedBuffer`; see
`docs/roadmap/fn3-architecture.md` and FN3-11). `execute_op` therefore uploads
the operands, dispatches on the GPU and downloads the result, and every record
says `host_staged = true`. That is **staging, not CPU computation**: the
arithmetic runs in the Vulkan kernels, proven by the submissions, dispatch
geometry and device-local bindings (timestamps are recorded when the queue
family supports them). Device-resident tensor storage
is #52/#48 work and is not claimed here.

## 6. No silent fallback and session isolation

- **A model prepared for Vulkan is never stepped by the CPU.**
  `Session::with_runtime` returns `DeviceMismatch { expected: vulkan(0), actual: cpu }`
  before allocating a cache or building a plan, and
  `PreparedModel::execute` refuses the same way. `Tensor::zeros` on a Vulkan
  device without a backend is `DeviceUnavailable`; it never substitutes host
  memory.
- **No usable driver.** A child process with
  `VK_ICD_FILENAMES`/`VK_DRIVER_FILES` pointed at a nonexistent manifest
  (so the loader really fails) gets:

  ```text
  (abridged only by `...`)
  device unavailable: requested device vulkan is unavailable: no Vulkan device is
  usable: Vulkan loader unavailable: vkCreateInstance failed:
  ERROR_INCOMPATIBLE_DRIVER (-9): ... Install a Vulkan ICD (`vulkan-icd-loader`
  and the GPU driver package), or point VK_ICD_FILENAMES at a valid ICD;
  `vulkaninfo --summary` shows what the loader sees; available devices: [cpu]
  ```

  The error names the request, the loader failure and the fix, and the process
  does not fall back to the CPU. (The host itself has a driver, so the condition
  is simulated at the loader level in a subprocess; it is the real
  `vkCreateInstance` failure path.)
- **Unsatisfiable explicit requests** (`vulkan(index=4294967295)`, a named
  adapter that does not exist) are `DeviceUnavailable` naming the request and
  the enumerated adapters, and `DeviceRequest::resolve` never returns `Cpu` for
  them.
- **Isolation.** Two sessions over one `PreparedModel` have distinct KV
  buffers, independent extents/counters and identical logits; a third session
  reproduces the first byte for byte. On the GPU the second session's prefill
  and first decode are compared with the first session's. A capacity failure
  leaves the extent, step, token count, phase and every cache byte identical
  (FNV-1a over all live KV bytes before/after).
